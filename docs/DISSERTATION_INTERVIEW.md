## 1. Постановка задачи

**Цель этапа:** после отбора по резюме (этап 1) провести **структурированное видео-интервью**: кандидат отвечает на фиксированный набор вопросов; система автоматически оценивает **содержание ответов** относительно эталона и требований вакансии.

**Не входит в этап 2:** анализ мимики/эмоций по видео (только текст из речи).

**Критерий прохождения:**

\[
\text{interview\_score\_avg} = \frac{1}{N}\sum_{i=1}^{N} \text{score}_i
\qquad
\text{approved} = (\text{interview\_score\_avg} \geq 7)
\]

`score_i` — целое число **0–10** по вопросу \(i\) (оценка LLM). Порог по умолчанию: **7** (`INTERVIEW_PASS_THRESHOLD`).

## 2. Сценарий интервью

### 2.1. Структура JSON

Файл сценария (например `data/interviews/scenarios/backend_developer.json` или загруженный HR для кампании `camp_{id}.json`):

```json
{
  "pass_threshold": 7,
  "questions": [
    {
      "question_id": "q_rest_api",
      "question": "Как вы проектируете REST API?",
      "reference_answer": "Эталонный текст: ключевые идеи, термины, подходы..."
    }
  ]
}
```

- **`question`** — показывается кандидату.
- **`reference_answer`** — ориентир для LLM (не дословное совпадение).
- Опционально **`vacancy_text`** в сценарии; иначе подставляется текст вакансии из `cleaned/transformer`.

### 2.2. Кто задаёт вопросы

HR может **загрузить свой JSON** в веб-приложении (вкладка «Сценарий интервью») или использовать шаблон, скопированный при создании кампании.

---

## 3. Поток в веб-приложении (основной сценарий)

### 3.1. Со стороны HR

1. Создание **кампании**: ссылка на вакансию hh.ru + **поисковая строка** для резюме.
2. Фоновая обработка: загрузка данных → pre-clean/clean → ранжирование (этап 1) → топ кандидатов.
3. (Опционально) загрузка файла с вопросами и эталонами.
4. **Приглашения**: выбор кандидатов из топа, email → создаётся учётка и сессия интервью; письмо SMTP или лог с паролем.
5. Просмотр **результатов**: средний балл, одобрен/не одобрен, оценки и комментарии LLM по каждому вопросу.

### 3.2. Со стороны кандидата

1. Вход по **email и паролю** из приглашения.
2. Экран **«Видео-собеседование»** — вопросы **по одному**.
3. На каждый вопрос: **камера → запись → ответ → «Следующий вопрос»**.
4. После последнего вопроса — автоматическое **завершение** и сообщение об обработке.

## 4. Запись видео: когда и как сохраняется

Полная таблица путей, формат WAV после ffmpeg, структура `transcript.json`, отдельная обработка на вопрос, пустой транскрипт → ошибка, текст в LLM: **[INTERVIEW_DETAILED.md §2](INTERVIEW_DETAILED.md#2-файлы-артефакты-и-цепочка-обработки-явно)**.

### 4.1. Момент записи

| Действие | Что происходит |
|----------|----------------|
| **«Включить камеру»** | Браузер получает поток с камеры и микрофона (`getUserMedia`), показывается превью. Запись **ещё не идёт**. |
| **«Запись»** | Стартует `MediaRecorder` (обычно **WebM**, видео + аудио). Кандидат отвечает на текст вопроса на экране. |
| **«Следующий вопрос»** | Запись **останавливается**; файл **сразу отправляется** на сервер. Затем показывается следующий вопрос. |

**Один файл = один вопрос.** Не один длинный ролик на всё интервью.

До нажатия «Следующий вопрос» видео хранится **только в памяти браузера**, на сервер не передаётся.

### 4.2. Сохранение на сервере

Запрос: `POST /api/interviews/me/questions/{question_id}/video` (multipart, файл WebM).

Путь на диске:

```text
data/interviews/{interview_uid}/questions/{question_id}/raw.webm
```

`interview_uid` создаётся при приглашении (например `int_a1b2c3d4e5f6`).

## 5. Обработка после завершения интервью

Триггер: `POST /api/interviews/me/complete` (после загрузки видео по **всем** вопросам).

Для **каждого** вопроса **в фоне**:

| Шаг | Инструмент | Результат |
|-----|------------|-----------|
| 1. Аудио | **ffmpeg** | `audio_16k.wav` (16 kHz, mono) |
| 2. Распознавание | **Whisper** | `transcript.json` (полный текст + сегменты с таймкодами) |
| 3. Оценка | **Groq** (`ChatGroq`, Llama 3.3 70B) | `evaluation.json`: `score` (0–10), `summary` (рус.) |

Затем **finalize**: средний балл, `approved`, файл `interview_summary.json` и запись в БД для HR.

### 5.1. Промпт оценки (суть)

LLM сравнивает **транскрипт ответа** с **эталоном** и **текстом вакансии**:

- оценка по **смыслу**, не по совпадению слов;
- учёт ошибок ASR (не штрафовать за опечатки при ясном смысле);
- критерии: корректность, полнота, глубина, практика, ошибки, релевантность вакансии;
- ответ строго в JSON: `{ "score": 0-10, "summary": "..." }`.

Полный текст: `services/interview/prompts.py`.

### 5.2. Интерпретация балла (для текста)

| score | Смысл |
|-------|--------|
| 0–2 | Неверно / не по теме |
| 3–4 | Слабо, серьёзные пробелы |
| 5–6 | Частично верно, базовый уровень |
| 7–8 | Хороший профессиональный ответ |
| 9–10 | Глубокое экспертное понимание |

## 6. Структура данных (артефакты)

```text
data/interviews/scenarios/           # сценарии (вопросы + эталоны)
data/interviews/{interview_uid}/
  meta.json                          # interview_id, candidate_id, query
  interview_summary.json             # итог: avg, approved, questions[]
  questions/{question_id}/
    raw.webm                         # загруженное видео
    audio_16k.wav                    # после ffmpeg
    transcript.json                  # Whisper
    evaluation.json                  # Groq: score, summary
data/results/interviews/             # копия итога для отчётов
```

## 8. Связь с этапом 1

| Этап 1 | Этап 2 |
|--------|--------|
| Ранжирование резюме ↔ вакансия | Оценка устных ответов по вопросам |

## 10. Что писать в главе (чеклист)

1. Место этапа 2 в общей системе скрининга (после LTR по резюме).  
2. Структурированное интервью: N вопросов, эталонные ответы.  
3. Схема «видео → аудио → текст → LLM-судья».  
4. **Когда** идёт запись (по вопросам, в браузере) и **когда** файл попадает на сервер.  
5. Формула среднего балла и порог одобрения (≥ 7).  
6. Ограничения: оценка по транскрипту, не по видео; зависимость от качества ASR.  
7. Пример полей `evaluation.json` / `interview_summary.json`.  
8. (Опционально) скриншоты веб: вопрос, запись, результаты у HR — см. [WEB_APP.md](WEB_APP.md).
