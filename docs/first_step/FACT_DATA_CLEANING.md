# Факт: очистка и подготовка данных (резюме и вакансии)

Описание строго соответствует коду в `services/preprocessing/*.py` и тем файлам, которые затем используются в первом и втором этапах.

---

## 1. Резюме

### 1.1. Pre-clean резюме

Файл: `services/preprocessing/pre_clean_resumes.py`

- **Вход:** `data/raw/full/resumes/resumes_*.json`  
  Это «сырые» полные резюме с hh.ru (вся структура API).
- **Выход:** `data/prepared/resumes/pre-cleaned/resumes_*.json`

Из каждого резюме удаляются поля, которые не нужны для текста и признаков, в том числе:

- персональные и чувствительные: `last_name`, `first_name`, `middle_name`, `photo`, …  
- технические и служебные: `negotiations_history`, `actions`, `alternate_url`, `download`, `owner`, `created_at`, `updated_at`, `real_id`, …  
- поля интерфейса и рекомендации: `tags`, `district`, `portfolio`, `site`, `view_without_contacts_reason`, …  

Результат: структура становится компактнее, сохраняются id, опыт, позиции, навыки и другие смысловые поля.

### 1.2. Clean резюме → classical + transformer

Файл: `services/preprocessing/clean_resumes.py`

- **Вход:** `data/prepared/resumes/pre-cleaned/resumes_*.json`
- **Выход:**
  - classical: `data/prepared/resumes/cleaned/classical/resumes_<query>.json`
  - transformer: `data/prepared/resumes/cleaned/transformer/resumes_<query>.json`

#### 1.2.1. Нормализация и лемматизация

Используются:

- `TECH_ALIASES` — словарь регулярных выражений для приведения технологических синонимов к одной форме (например, разные написания одного и того же фреймворка или стека).
- `pymorphy3.MorphAnalyzer` — морфологический анализатор для русских слов.
- `RUSSIAN_STOP_WORDS` — фиксированный набор русских стоп‑слов.

`smart_lemmatize(text)`:

1. Применяет все замены из `TECH_ALIASES` (регистронезависимо).
2. Токенизирует текст на слова (латиница, кириллица, цифры, `._-`).
3. Удаляет стоп‑слова (только для русских слов).
4. Для чисто русских слов пробует взять **нормальную форму** через `morph.parse(...)[0].normal_form`, иначе оставляет как есть.
5. Для остальных токенов (английские tech‑термины и т.п.) просто приводит к нижнему регистру.
6. Склеивает в строку через пробел.

`normalize_for_classical(text)`:

- применяет `smart_lemmatize`,
- схлопывает повторные пробелы.

`normalize_for_transformer(text)`:

- применяет только `TECH_ALIASES`,
- схлопывает пробелы,
- **без лемматизации**, чтобы сохранить форму текста для эмбеддингов.

#### 1.2.2. Classical формат резюме

Каждое резюме в `RESUMES_CLASSICAL` (`resumes_<query>.json`) имеет поля:

- `id` — идентификатор резюме;
- `query` — тег запроса (например, `backend_developer`);
- `total_experience_months` — суммарный опыт в месяцах (`total_experience.months`);
- `title` — нормализованный заголовок резюме (`normalize_for_classical`);
- `skills` — конкатенация нормализованных:
  - навыков из `skill_set`;
  - языков (`language.name` + уровень), приведённых к нижнему регистру;
- `experience` — нормализованный текст описаний опыта (склейка `description` из всех записей `experience`);
- `positions` — список нормализованных названий позиций из записей `experience`.

Именно эти поля используются в classical‑пайплайне (BM25 / TF‑IDF) в первом этапе.

#### 1.2.3. Transformer формат резюме

Каждое резюме в `RESUMES_TRANSFORMER` (`resumes_<query>.json`) имеет:

- те же `id`, `query`, `total_experience_months`;
- **`text`** — короткий конспект для би-encoder (E5, MiniLM, …):
  - `Должность`, `Навыки` (`skill_set`), `Языки`;
  - `Позиции` (уникальные `experience[].position`);
  - `Опыт:` — усечённые `description` последних **2** мест (лимит символов в `pipeline_config`);
- **`text_rerank`** — то же + чуть больше опыта (**3** места, больший лимит) для cross-encoder.

Поле `skills` (проза кандидата с hh) **не** используется — только `skill_set`.

При encode к `text` / `text_rerank` дописывается строка с суммарным стажем в месяцах (`append_experience_to_resume_text`) — **только transformer**, не classical.

## 2. Вакансии

### 2.1. Pre-clean вакансий

Файл: `services/preprocessing/pre_clean_vacancies.py`

- **Вход:** `data/raw/full/vacancies/vacancies_*.json`
- **Выход:** `data/prepared/vacancies/pre-cleaned/vacancies_*.json`

Удаляются поля:

- служебные и биллинговые: `premium`, `billing_type`, `insider_interview`, `auto_response`, `response_url`, `adv_response_url`, `code`, `created_at`, `published_at`, …;
- контакты и чувствительные данные: `contacts`, `employer` (потом приводится к `{id, name}`), `area`, …;
- поля интерфейса сайта.

Поле `description` очищается:

- `BeautifulSoup(html, \"html.parser\").get_text(separator=\"\\n\")` → многострочный текст без HTML‑разметки.

Списки `key_skills`, `languages`, `work_format`, `work_schedule_by_days`, `working_hours` приводятся к спискам строк (имён).

Поля `employment`, `experience`, `schedule` приводятся к их `name` (текстовые описания, как на hh «Полная занятость», «От 3 до 6 лет» и т.п.).

### 2.2. Clean вакансий → classical + transformer

Файл: `services/preprocessing/clean_vacancies.py`

- **Вход:** `data/prepared/vacancies/pre-cleaned/vacancies_*.json`
- **Выход:**
  - classical: `data/prepared/vacancies/cleaned/classical/vacancies_<query>.json`;
  - transformer: `data/prepared/vacancies/cleaned/transformer/vacancies_<query>.json`.

#### 2.2.1. Нормализация текста

`normalize_for_classical(text)`:

- применяет `TECH_ALIASES` (технологические синонимы),
- приводит к нижнему регистру,
- удаляет небуквенно‑цифровые символы (оставляя пробелы),
- схлопывает пробелы.

`normalize_for_transformer(text)`:

- только `TECH_ALIASES` и нормализация пробелов, без лемматизации и жёсткого lower‑casing.

#### 2.2.2. Classical формат вакансий

`build_vacancy_classical(vacancy)` создаёт словарь:

- `id`, `query`;
- `title` — нормализованный `name` вакансии;
- `skills` — нормализованный текст из `key_skills` (список имён навыков);
- `requirements` — нормализованный текст требований:
  - сначала `extract_requirements_from_description(description)` выдёргивает блок «Требования» / «Нужно» / «Должен» и т.п. из очищенного HTML‑описания;
  - если не получилось, используется весь `description`;
- `experience_text` — исходная строка опыта (как на hh, «От 3 до 6 лет» и т.п.);
- `min_experience_months`, `max_experience_months` — результат `parse_experience_text(experience_text)`:
  - «более X лет» → `min = X * 12`, `max = None`;
  - «от X до Y лет» → `min = X * 12`, `max = Y * 12`;
  - «X лет» → `min = max = X * 12`;
  - «нет опыта» / «без опыта» → `min = 0`, `max = None`;
  - прочие случаи → `min = max = None`.

Именно эти поля используются в classical‑пайплайне (BM25/TF‑IDF) и в фильтре по опыту первого этапа.

#### 2.2.3. Transformer формат вакансий

`build_vacancy_transformer(vacancy)` создаёт:

- `id`, `query`;
- `text`, который конструируется как:
  - `Должность: <name>`;
  - `Ключевые навыки: <нормализованный список навыков>` (через `normalize_for_transformer`);
  - `Требования: <обрезанный фрагмент требований>` (максимум 500 символов из блока требований);
  - `Требуемый опыт: <experience>` — та же строка, что на hh;
- `min_experience_months`, `max_experience_months` — такие же значения, как в classical.

Этот `text` затем используется:

- для расчёта эмбеддингов (E5, MiniLM, ruSBERT, MPNet) в первом этапе;
- для составления текста вакансии в парах с резюме на втором этапе (cross-encoder), с добавлением информации об опыте через `append_experience_to_vacancy_text`.
