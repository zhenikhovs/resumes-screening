# Проект: этап 2 — видеоинтервью и оценка ответов (теоретический пайплайн)

Документ **не описывает реализованный код** в репозитории. Это **проектная спецификация** второго этапа отбора: запись интервью, преобразование речи в текст, сегментация на вопросы и ответы, сопоставление с эталонными ответами и выставление оценки.

---

## 1. Цель этапа

После отбора кандидатов по резюме (этап 1) провести **структурированное интервью** (видео + аудио), автоматически извлечь **ответы кандидата по каждому вопросу** и **сравнить** их с заранее заданными критериями / эталонными формулировками, получив **числовую или пороговую оценку** пригодности.

---

## 2. Входные данные (конфигурация интервью)

| Сущность | Назначение |
|----------|------------|
| **Сценарий интервью** | Упорядоченный список блоков: приветствие, вопрос 1…N, прощание. |
| **Вопрос** | Текст (и при необходимости TTS-озвучка), тип (открытый, кейс, да/нет), **ожидаемая длительность ответа**. |
| **Эталон** | Для каждого вопроса: ключевые тезисы, допустимые формулировки, «красные флаги», опционально **embedding эталонного ответа** или несколько эталонных парафразов. |
| **Пороги** | Минимальный балл по вопросу / по всему интервью для прохождения этапа. |

Сценарий и эталоны хранятся отдельно от записи (JSON/YAML в репозитории или БД).

---

## 3. Запись интервью

### 3.1. Каналы

- **Видео:** основной поток (лицо кандидата, при необходимости экран).
- **Аудио:** либо дорожка из того же контейнера (MP4/WebM), либо отдельный микрофонный поток (WAV/FLAC) для лучшего качества ASR.

### 3.2. Требования к записи

- Частота дискретизации аудио **16 kHz** (или 48 kHz с последующим ресэмплингом) — стандарт для большинства ASR.
- Моно или стерео; для диаризации (разделение интервьюер/кандидат) предпочтительно **два канала** или отдельная запись голоса кандидата.
- Метаданные файла: `interview_id`, `candidate_id`, `vacancy_id`, `started_at`, `duration_sec`, `codec`.

### 3.3. Хранение

- Сырой файл: `storage/interviews/{interview_id}/raw_video.mp4` (+ опционально `raw_audio.wav`).
- Контрольная сумма / хеш для целостности.

---

## 4. Извлечение аудио из видео

Если есть только видео:

1. **FFmpeg** (или аналог): извлечь аудиодорожку  
   `ffmpeg -i raw_video.mp4 -vn -acodec pcm_s16le -ar 16000 -ac 1 interview_16k_mono.wav`
2. Нормализация громкости (опционально, `loudnorm`) для стабильности ASR.

Результат: **`interview_16k_mono.wav`** — вход для распознавания речи.

---

## 5. Распознавание речи (ASR)

### 5.1. Варианты движка

- **Облачные API** (высокое качество для русского): Yandex SpeechKit, Google Speech-to-Text, Azure и т.п.
- **Локальные модели:** Whisper (large-v3 и др.), Vosk — для офлайн и воспроизводимости.

### 5.2. Режим работы

- **Полный файл** → один проход с таймкодами слов/фраз (**word- или segment-level timestamps**).
- Выход: список сегментов  
  `{ "t_start": float, "t_end": float, "text": str, "confidence": float? }`.

### 5.3. Постобработка текста

- Нормализация чисел и аббревиатур (по словарю домена).
- Удаление слов-паразитов на уровне эвристик (опционально, чтобы не портить семантику — осторожно).

Итог: **`transcript.json`** — полная расшифровка с временными метками.

---

## 6. Разделение «вопрос интервьюера — ответ кандидата»

### 6.1. Если известен сценарий по времени

Если интерфейс интервью фиксирует **моменты нажатия «следующий вопрос»**:

- На запись накладываются маркеры `t_q1_start`, `t_a1_expected_start`, …
- Ответ кандидата для вопроса *i*: сегменты транскрипта с  
  `t_start ∈ [t_after_question_i, t_before_question_{i+1}]`,  
  с вычитанием паузы на озвучку вопроса (2–5 с).

### 6.2. Если маркеров нет — диаризация + детекция вопросов

1. **Диаризация** (pyannote, Whisper speaker labels и т.д.): метки «спикер A / спикер B»; интервьюер обычно задаёт вопросы короткими репликами, кандидат — длинными монологами.
2. **Сопоставление с текстом вопроса:** для каждого блока интервьюера fuzzy-match или embedding-сходство фразы из транскрипта с текстом вопроса из сценария → привязка временного окна.
3. **Окно ответа:** от конца реплики интервьюера до начала следующего вопроса или до таймаута (например 120 с).

### 6.3. Выход сегментации

Структура **`qa_segments.json`**:

```json
[
  {
    "question_id": "q_backend_scaling",
    "t_question_end": 125.4,
    "t_answer_start": 128.0,
    "t_answer_end": 198.7,
    "answer_text": "…сплошной текст ответа кандидата…"
  }
]
```

## 7. Сравнение ответа с эталоном

### 7.1. Уровни оценки

| Уровень | Идея | Плюсы / минусы |
|---------|------|----------------|
| **Ключевые слова** | Наличие обязательных терминов из эталона | Просто; слабо для перефразирования |
| **Embedding similarity** | Косинус между эмбеддингом ответа и эталона | Устойчивее к формулировкам; нужен хороший мультиязычный энкодер |
| **Cross-encoder** | Пара (вопрос + ответ кандидата) vs (вопрос + эталонный ответ) | Ближе к «релевантности»; дороже |
| **LLM-as-judge** | Промпт: «оцени полноту и корректность по рубрике 1–5» | Гибко; нужна валидация и воспроизводимость |

Рекомендуемая **практическая связка:**  
embedding similarity **+** проверка **обязательных концептов** (список лемм/сущностей из эталона) **+** порог.

### 7.2. Формула балла (пример)

Для вопроса \(i\):

\[
\text{score}_i = w_1 \cdot \text{sim}_{\text{emb}}(\text{answer}_i, \text{reference}_i) + w_2 \cdot \text{coverage}(\text{must\_have\_terms}, \text{answer}_i) - w_3 \cdot \text{penalty}(\text{forbidden\_phrases})
\]

- `sim_emb` ∈ [0, 1] после нормализации.
- `coverage` — доля найденных обязательных терминов (или F1 по сущностям).
- Итог по интервью: взвешенная сумма \(\sum_i \alpha_i \text{score}_i\) или «все обязательные вопросы ≥ τ».

### 7.3. Выход

- **`scores.json`**: по каждому `question_id` — числовой балл, флаги «пройден / не пройден».
- **`interview_summary.md` или JSON**: агрегат, рекомендация рекрутеру.

---

## 8. Сквозной пайплайн (блок-схема)

1. **Инициализация** — загрузить сценарий и эталоны для `vacancy_id` / типа позиции.  
2. **Запись** — сохранить видео/аудио, метаданные.  
3. **Extract audio** — WAV 16 kHz mono.  
4. **ASR** — `transcript.json` с таймкодами.  
5. **Align Q&A** — `qa_segments.json` (по маркерам UI или диаризация + match к тексту вопроса).  
6. **Score** — для каждого сегмента сравнение с эталоном → `scores.json`.  
7. **Decision** — порог прохождения этапа 2; логирование для аудита.

---

## 9. Нефункциональные требования

- **Согласие и ПДн:** явное согласие на запись и обработку голоса/изображения; политика хранения и удаления.
- **Воспроизводимость:** фиксировать версии моделей ASR и эмбеддеров.
- **Человек в контуре:** при спорных баллах — ручная перепроверка фрагмента записи.

---

## 10. Связь с этапом 1

Кандидаты, прошедшие **ранжирование по резюме** (топ‑K или порог), попадают в очередь на **этап 2**; идентификаторы `resume_id` / `candidate_id` связывают JSON этапа 1 с артефактами интервью (`interview_id`).
